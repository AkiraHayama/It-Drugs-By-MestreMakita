# it-drugs

## Propósito
Sistema avançado de drogas: plantio (sementes -> plantas -> colheita), processamento em mesas de crafting (ex.: weed -> joint, coca -> cocaine), uso de drogas (efeitos temporários) e um dealer de sementes com peds. Possui também sistema de venda para NPCs (`Config.EnableSelling`, mas desativado por padrão no config pois o servidor usa `qbx_drugs` para vendas).

## Dependências
- Declaradas no `fxmanifest.lua`: `ox_lib`, `oxmysql`.
- Detectadas em runtime via `bridge/init.lua` (camada de compatibilidade "bridge", suporta qb-core ou es_extended, e ox_inventory ou qb-inventory automaticamente por `GetResourceState`).
- Integração opcional com `ox_target` ou `qb-target` (`Config.Target`, atualmente `'ox_target'`).
- Integração opcional com `ps-dispatch` (verificado via `GetResourceState`, não é dependência obrigatória).

## Exports (client e server)
Não expõe `exports()` do FiveM. Toda a API interna fica na tabela global `it` (bridge), usada só internamente. Comunicação com outros resources é feita via `lib.callback` (ox_lib):
- `it-drugs:getPlayerName`, `it-drugs:getCitizenId`, `it-drugs:getLicences`, `it-drugs:getLicence` (server)
- `it-drugs:hasItem`, `it-drugs:getItemCount`, `it-drugs:server:getItemLabel` (server)
- `it-drugs:client:getItemLabel` (client)

## Eventos principais (client->server / server->client)
- `it-drugs:server:initiatedrug` (client->server) — inicia plantio/colheita.
- `it-drugs:client:showDealerMenu` (server->client, disparado pelo target do ped) — abre a loja do dealer via `exports.ox_inventory:openInventory('shop', { type = 'it_drugs_<dealerId>' })`.
- `it-drugs:server:createNewLamp` / `it-drugs:server:takeLamp` (client->server) — colocar/recolher lâmpada de cultivo.
- `it-drugs:toggleItem` (client->server) — dar/remover item consumível (usado pela bridge de itens).
- Server chama `SendPoliceAlert()` (definida em `shared/config.lua`) que dispara `exports['ps-dispatch']:DrugDealing()` quando o dealer é acionado, se `ps-dispatch` estiver rodando.

## Loja do dealer (via ox_inventory)
- O dealer de sementes **não usa NUI própria** — tentamos um painel HTML/CSS/JS customizado, mas não renderizava no servidor de produção mesmo com o Lua funcionando 100% (debugado extensivamente: `SetNuiFocus`/`SendNUIMessage` executavam sem erro, `refresh`+`restart`, reconexão completa do cliente, nada resolveu). Trocamos pra reaproveitar a loja nativa do `ox_inventory` (`exports.ox_inventory:RegisterShop`/`openInventory('shop', ...)`), que já é comprovadamente funcional (mesma NUI do inventário do jogador).
- Em `server/sv_dealer.lua`: no boot, pra cada dealer em `Config.DrugDealers`, gera os preços aleatórios (como antes) e registra uma shop location-less via `exports.ox_inventory:RegisterShop('it_drugs_' .. dealerId, { name = ..., inventory = {{name, price, currency = 'money'}, ...} })`. `currency = 'money'` é o item de dinheiro físico do ox_inventory — só compra com cash na mão, nunca banco.
- Em `client/cl_dealer.lua`: `it-drugs:client:showDealerMenu` chama `exports.ox_inventory:openInventory('shop', { type = 'it_drugs_' .. dealerId })`. Só funciona se `it.inventory == 'ox'` (guard explícito); não há fallback pra qb-inventory.
- Compra em si (descontar dinheiro, dar item) é 100% responsabilidade do `ox_inventory`, não passa mais por eventos próprios do it-drugs.

## Configuração
Arquivo único `shared/config.lua`:
- `Config.Target` (ox_target/qb-target/false), `Config.Language`, `Config.Webhook` (Discord).
- `Config.DrugDealers` (peds, localizações, blips, itens vendidos).
- Plantio: `Config.Zones` (zonas exclusivas por droga), `Config.AllowedGrounds`, `Config.PlantTypes`, `Config.Plants` (sementes -> produtos), `Config.PlayerPlantLimit`, decaimento de água/fertilizante. Crescimento depende da média entre `Config.SunlightZones`/`Config.DefaultSunlight` (+ luz de `Config.Lamps`), água e fertilizante — ver `server/sv_planting.lua`.
- **Menu da planta agora mostra "Luz" e se o local é Ao Ar Livre ou Ambiente Fechado**: `client/cl_menus.lua:getLightOptions(plantData)` monta uma barra de progresso (sol + lâmpada somados, mesmo valor que já era usado no cálculo de crescimento/saúde, só que nunca tinha sido exposto pro jogador) mais um aviso de texto - "Ao Ar Livre" se `plantData.sunlight >= Config.IndoorSunlightThreshold` (40 por padrão), senão "Ambiente Fechado" (avisando que precisa de lâmpada). Anexado nos TRÊS estados do `showPlantMenu` (morta/pronta/crescendo). Precisou expor `sunlight`/`addedLight` nos três callbacks que retornam dados de planta (`GetPlantInPot`, `getPlantData`, `getPlantDataWithId` em `sv_planting.lua`) - esses campos já existiam e já eram usados internamente pro cálculo, só nunca tinham sido incluídos no retorno pro client antes. `Config.IndoorSunlightThreshold` só afeta esse texto/aviso, não muda o cálculo real de crescimento/saúde (que já soma os dois valores direto).
  - **Bug corrigido nesse processo: plantas nascendo em lugar fechado (ex: estacionamento com teto alto) vinham com sunlight parcial (~40%) em vez de 0%.** `calculateSunlight` (duplicada em `client/cl_pots.lua` e `client/cl_planting.lua`) manda um raio pra cima (50m) e antes calculava `skyFactor` PROPORCIONAL à distância até bater num teto (`distanceToHit / 50.0`) - só zerava mesmo se o teto estivesse a menos de 5m. Um teto alto (tipo garagem de vários andares) dava luz "parcial" mesmo sendo 100% fechado, sem sol direto nenhum ali. Corrigido pra binário: bateu em QUALQUER coisa acima (`hit == 1`) = fechado = `skyFactor = 0.0`, só dá luz plena (`1.0`) se o raio não bater em nada (céu aberto de verdade). Luz indoor agora só vem de lâmpada (`Config.Lamps`/`addedLight`), como pedido.
  - **Bug maior achado logo em seguida: planta EM VASO, mesmo a céu aberto, nascia sempre com sunlight 0 (sempre "fechada").** Causa: o vaso tem colisão sólida de verdade (mesma colisão usada pelo alvo "Usar Vaso"/`addModel`), e `calculateSunlight` (`client/cl_pots.lua`) mandava o raio pra cima começando EXATAMENTE na coordenada do vaso, sem excluir o próprio vaso do teste (`StartShapeTestRay(..., 273, 0, 0)` - 8º parâmetro, entidade ignorada, era sempre `0`/nenhuma) - o raio batia na parede/borda do próprio vaso antes de escapar pra cima, então TODA planta em vaso era detectada como "fechada" não importa onde estivesse (só o plantio direto no chão, sem vaso, não tinha esse problema, por isso não foi pego nos testes anteriores). Corrigido: `calculateSunlight(coords, ignoreEntity)` agora aceita a entidade a ignorar, e a chamada em `RegisterNetEvent('it-drugs:client:plantInPot', ...)` passa o próprio `entity` (o vaso) - `calculateSunlight(GetEntityCoords(entity), entity)`.
  - **Luz de lâmpada agora sobe aos poucos em vez de instantânea** (pedido do usuário: "de 20 em 20 até 100%"). Antes, `RecalculatePlantsLight` (`server/sv_planting.lua`) setava `addedLight` direto pro valor calculado pela distância (`calculateAddedLight`) assim que uma lâmpada era colocada/removida ou a planta nascia perto de uma já existente. Agora esse valor calculado vira só o TETO (`plants[k].targetAddedLight`, campo novo, só em memória - não precisou migração de banco) e o `addedLight` de verdade sobe `Config.LampLightRampStep` (20, padrão) por `Config.GrowthTickInterval` (30s) dentro de `updatePlantNeeds`, até alcançar o alvo (então ~2min30 pra chegar em 100% partindo de perto de uma lâmpada nova). Perder a lâmpada continua instantâneo (zera na hora em `RecalculatePlantsLight`, sem ramp de queda, só de subida). Toda planta nova (`createNewPlant`/`plantInPot`) já nasce com `addedLight = 0.0` mesmo que já tenha lâmpada por perto - também precisa ramping do zero. `setupPlants` (restart do resource) preserva o `addedLight` que já tinha sido acumulado, só `targetAddedLight` é recalculado do zero (via `RecalculatePlantsLight` chamado em `sv_lamps.lua:onResourceStart`, depois que `setupPlants` já rodou - ordem de `server_scripts` no `fxmanifest.lua` garante isso). Sol (`sunlight`, ao ar livre) NÃO usa esse ramp, continua instantâneo/no valor cheio desde a criação - só luz artificial de lâmpada simula "esquentar".
- **Quem mantém a planta viva: só água e luz.** A pedido do usuário, `calcHealth` (server/sv_planting.lua) foi redesenhado pra só olhar `water` e `sunlight + addedLight` (luz natural + lâmpada, mesmo `effectiveLight` usado no cálculo de crescimento) - `Config.WaterThreshold`/`Config.LightThreshold` (10% cada). Fertilizante NÃO entra mais nessa conta (`Config.FertilizerThreshold` foi removido do config, ficou sem uso). Isso dá propósito real às lâmpadas (`Config.Lamps`) pra vasos indoor: sem luz nenhuma (sol bloqueado + sem lâmpada por perto), a planta morre igual a ficar sem água.
- **Fertilizante agora só afeta a QUANTIDADE colhida, não a saúde.** `harvestPlant` mudou de `math.random(min, max)` fixo pra escalar linearmente com o nível de fertilizante no momento da colheita: `amount = min + (max - min) * (fertilizante / 100)`. Fertilizante 0% = colhe o mínimo, 100% = colhe o máximo. Antes o fertilizante não tinha nenhum efeito na colheita.
- **Bug corrigido: estado da planta não salvava ao reiniciar o resource/servidor.** `AddEventHandler('onResourceStop', ...)` em `sv_planting.lua` chamava `MySQL.update('UPDATE drug_plants SET water = (:water), fertilizer = (:fertilizer) WHERE id = (:id)', {...})` mas a tabela de parâmetros NUNCA incluía `id` - o `:id` no WHERE ficava sem valor, então a query não batia com nenhuma linha e o salvamento final não fazia nada (silenciosamente, sem erro visível). Corrigido pra passar `id` corretamente, e também passou a salvar `health`/`growth` nesse momento (antes só salvava água/fertilizante ali - o resto dependia só do último tick periódico de `updatePlantNeeds`, que já salvava certo mas só a cada `Config.GrowthTickInterval` segundos). Auditoria completa confirmou que esse era o ÚNICO lugar no sistema com esse tipo de bug (placeholder `:algumacoisa` na SQL sem parâmetro correspondente) - todas as outras queries do it-drugs (pots, processing, waterpoints, dryingracks, lamps) já passavam os parâmetros certos.
- **Bug corrigido: saúde decaindo em dobro.** `calcHealth` tinha dois blocos `if/elseif` praticamente idênticos, um embaixo do outro, cada um subtraindo `math.random(Config.HealthBaseDecay[1], Config.HealthBaseDecay[2])` sob a mesma condição - toda vez que a condição batia, os dois disparavam, decaindo a saúde duas vezes por tick. Removido o bloco duplicado. Junto com o tick de teste acelerado (ver abaixo), isso fazia plantas morrerem bem mais rápido que o esperado.
- **Crescimento redesenhado (não é mais baseado em água/luz/fertilizante médios, é baseado em TEMPO + fertilizante):** `Config.GrowthTickInterval = 30` (segundos, valor real, não é teste) controla o tick de `updatePlantNeeds` (`elapsed >= Config.GrowthTickInterval` e `SetTimeout(Config.GrowthTickInterval * 1000, ...)`, ambos lendo do config em vez de hardcoded). A cada tick, se a planta estiver viva (`health > 0`), o crescimento avança um passo pequeno e fixo calculado por `getFertilizerGrowTimeReduction(fertilizer)`: a planta fica pronta em `Config.GlobalGrowTime` minutos (hoje 15) com 0% de fertilizante médio, e esse tempo diminui conforme `Config.FertilizerGrowTimeReduction` (dois pontos-âncora configuráveis: `[50] = 3` minutos a menos em 50% de fertilizante -> 12min, `[100] = 5` minutos a menos em 100% -> 10min; interpolação linear em dois segmentos entre 0-50 e 50-100). Água e luz **não** entram mais na velocidade de crescimento - só decidem se a planta está viva (`calcHealth`); fertilizante não afeta mais a saúde, só a velocidade de crescimento E a quantidade colhida (`harvestPlant`). `Config.Plants.coca_seed.growthTime` ainda está em `0.2` (teste, era `45`) - não foi revertido, é um valor de override por semente separado do `Config.GlobalGrowTime`.
- Lâmpadas de cultivo: `Config.EnableLamps`, `Config.Lamps` (item, modelo, alcance, luz adicionada) — `server/sv_lamps.lua` + `client/cl_lamps.lua`. Sistema 100% genérico por config: qualquer entrada nova em `Config.Lamps` já funciona automaticamente em `sv_usableitems.lua`, `cl_target.lua` e no cálculo de luz (`calculateAddedLight` em `sv_planting.lua`), sem precisar tocar em código. Hoje tem duas: `portable_lamp` (`bzzz_world_of_lamps_purple`, alcance 10, luz 70 - trocado do prop nativo do GTA pra essa lâmpada roxa de verdade do pacote `bzzz_lights_and_lamps`, dependency nova; outras cores disponíveis no mesmo pacote: `bzzz_world_of_lamps_{blue,green,orange,pink,red,white,yellow}`) e `reflector_lamp` (`xm_prop_base_tripod_lampb`, alcance 15, luz 80, ainda nativo do GTA) — a "Portable Lamp" do lunar_drugscreator (tripé com tubo de luz; a `reflector_lamp` é a variante com o refletor atrás do tubo que direciona a luz, por isso mais forte/focada), usam props NATIVOS do GTA (DLC de Natal), não precisam da dependência `lunar_drugscreator_props`. A antiga `grow_lamp` (`prop_worklight_02a`) foi removida a pedido do usuário — se algum vaso/planta indoor antigo dependia dela, precisa recolocar uma lâmpada nova (`portable_lamp`/`reflector_lamp`) por perto.
- Vasos de plantio: `Config.EnablePots`, `Config.Pots` (item, modelo vazio, modelo com terra, item de terra, altura) — `server/sv_pots.lua` + `client/cl_pots.lua`. Deixa plantar em qualquer lugar (indoor, em cima de móvel etc.), pulando a checagem de tipo de chão (`Config.OnlyAllowedGrounds`); NÃO pula o cálculo de luz solar, então planta em vaso indoor ainda precisa de uma lâmpada (`Config.Lamps`) por perto pra crescer rápido. Fluxo em DOIS passos: usar item `vaso` (posiciona vazio, `Config.Pots[x].model`, sem checagem de chão) -> target no vaso -> se `hasSoil` for falso, só aparece a opção "Colocar Terra" (consome `Config.Pots[x].soilItem`, evento `it-drugs:server:addSoil`) -> ao colocar terra, o PROP DE VERDADE é trocado: `sv_pots.lua` apaga a entidade vazia e cria uma nova com `Config.Pots[x].soilModel` no lugar (mesmo esquema de `updatePlantProp` em `sv_planting.lua` - delete+recria, move a entrada do cache pra chave da entidade nova), e só então marca `hasSoil = 1` em `drug_pots` -> depois de ter terra, aparece "Plantar Semente" (lista só as sementes que você tem) -> escolhe a semente -> consome só a semente e a planta nasce na MESMA altura configurada em `Config.Pots[x].heightOffset`. **Depois de plantada, o próprio menu do vaso mostra os controles de água/fertilizante/colheita direto** (`server/sv_planting.lua:GetPlantInPot` + callback `it-drugs:server:getPlantDataByPot`, `client/cl_menus.lua:showPotMenu` chama `TriggerEvent('it-drugs:client:showPlantMenu', plantData)` e retorna cedo) - é o MESMO menu que abre quando você mira na planta direto (barras de progresso clicáveis pra água/fertilizante, botão de colher quando pronta), só que acessível pelo vaso também, sem precisar sair e mirar na planta separadamente. (não existe mais offset por semente - `Config.Plants[seed].potHeightOffset` foi removido, a planta sempre nasce alinhada com o vaso). Como o vaso troca de model dinamicamente, `cl_target.lua` registra o alvo tanto pro `model` quanto pro `soilModel` (senão o vaso para de responder ao alvo depois de trocar). Depois de plantada, a planta é uma entrada normal em `drug_plants` (com `potId` preenchido) e usa todo o sistema de água/fertilizante/colheita já existente via o próprio modelo da planta. Colher/destruir a planta não afeta o vaso nem a terra (dá pra plantar de novo direto, só gastando semente de novo). Recolher o vaso (`it-drugs:server:takePot`) só é permitido se não tiver planta ativa nele, e o vaso recolhido "perde a terra" (linha inteira é apagada de `drug_pots`; se plantar um vaso novo, nasce vazio e `hasSoil` de novo falso).
